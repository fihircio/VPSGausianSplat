# Database: SQLite locally, Postgres by configuration

The backend talks to its database through SQLAlchemy only. **Which database it uses is decided by
`DATABASE_URL` alone** — there is no SQLite-specific code path, no raw SQL, and no Postgres-only column
type in the models (IDs are `String(36)` UUIDs, timestamps are `DateTime`, defaults are `func.now()`).

| Where | `DATABASE_URL` | Why |
|---|---|---|
| Code default (`backend/utils/config.py`) and `backend/.env.example` | `postgresql+psycopg://vps:vps@localhost:5432/vps` | Postgres remains the assumed production database |
| The Windows PC's `backend/.env` (gitignored) | `sqlite:///./backend/storage/vps.db` | No admin rights to run a service; local dev only |

`psycopg` stays in `backend/requirements.txt` so switching back needs no install step.

## Why SQLite on the PC

- The PC has **no admin rights**: Postgres had to be installed as a portable binary and started by hand
  after every reboot (`pg_ctl -D C:\pgsql_data`). SQLite removes that whole failure mode.
- One operator, one process host. The workload is a handful of API calls around a long GPU/pipeline job.
- The database file is one artefact to back up, and the data it holds (scenes, frames, anchors, tenants,
  API keys) is small.

## SQLite settings applied automatically

`backend/utils/db.py` listens on `connect` for `sqlite` URLs and sets:

| Pragma | Value | Reason |
|---|---|---|
| `journal_mode` | `WAL` | Readers (API requests) keep working while the pipeline thread writes progress |
| `synchronous` | `NORMAL` | The safe pairing with WAL for a workstation |
| `busy_timeout` | `15000` ms | A competing writer waits instead of raising `database is locked` |
| `foreign_keys` | `ON` | Matches the referential behaviour Postgres enforces |

Without WAL and a busy timeout, the scene pipeline (a daemon thread in `routes_scene.py`) and the API's
request threads contend for the same file and intermittently fail mid-processing.

## When to switch to Postgres

Switch **before** any of these becomes true:

- More than one process writes to the database (multiple uvicorn workers, Celery workers, a second
  service, a second operator).
- The database file would live on a network/shared volume, or more than one replica would mount it.
- You are serving anyone other than yourself, or you need point-in-time recovery.

```bash
# 1. Create the role and database
psql -U postgres -c "CREATE ROLE vps LOGIN PASSWORD '...'"
psql -U postgres -c "CREATE DATABASE vps OWNER vps"

# 2. Point the backend at it (backend/.env or the host's environment)
DATABASE_URL=postgresql+psycopg://vps:<password>@<host>:5432/vps

# 3. Restart the API — init_db() creates the tables on boot
```

Data does not migrate itself. Scene/frame/anchor rows can be regenerated by re-running the pipeline,
but tenants, API keys, and hand-placed anchors cannot — export them first if they matter:

```bash
python -c "import sqlite3, json; ..."   # or: sqlite3 backend/storage/vps.db .dump > dump.sql
```

## Deployment notes (containers, RunPod, managed hosts)

- **Never** put the SQLite file on a network volume and share it between pods. File locking over
  NFS/CIFS-style mounts is unreliable and can corrupt the database. SQLite is single-host by design.
- A RunPod **pod-local** SQLite file works for a single-replica demo, but it is lost when the pod is
  rebuilt; treat it as scratch.
- GPU workers should stay **stateless**: they take a job, read inputs from object storage, write
  outputs back, and report status through the API. Then only the API host needs a database — and that
  host should use a managed Postgres (or a Postgres sidecar/container with a persistent volume).
- The storage layer is already abstracted behind `get_storage()` (local ⇄ S3/Azure), so splitting
  compute from storage does not require changes to the pipeline.

## Schema management

`init_db()` calls `Base.metadata.create_all()` on startup — that is the mechanism the app actually uses;
it creates missing tables but never alters existing ones.

`backend/alembic/` contains baseline migrations that are **not** wired into startup and have no
`versions/` directory populated by the running app. Until that is exercised, any model change on an
existing database needs a manual `ALTER TABLE` (or a fresh database). Regenerate and adopt Alembic
before the first real deployment, otherwise schema drift becomes invisible.
