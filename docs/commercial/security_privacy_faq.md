# Security & Privacy FAQ

This FAQ is intended for pilot customers and procurement teams evaluating the VPS Spatial Platform. It reflects the current MVP/pilot stage of the product. We will update this document as the platform matures.

---

## 1. Where is scan and spatial map data stored?

Data storage depends on the deployment configuration chosen for your pilot:

| Mode | Where data lives |
|---|---|
| **LOCAL** (default) | On-premises on the server we set up for your pilot. No data leaves that machine. |
| **S3** | AWS S3 bucket, in the region you specify. We can use your own bucket under your AWS account. |
| **AZURE** | Azure Blob Storage container, in the region you specify. We can use your own storage account. |

We default to LOCAL for all pilots unless you request cloud storage. The storage mode is locked at deployment and does not change during the pilot.

---

## 2. Who has access to the spatial maps?

Access is controlled by:

- **API Key authentication** — every API call to create, process, or query a scene requires a valid `X-API-Key` header. The API key is generated by us at pilot setup and shared only with authorised personnel.
- **Network access** — the backend can be deployed on a private network (VPN-gated or air-gapped) if required. No public cloud endpoint is mandatory.
- No multi-tenant sharing: your scenes are not shared with any other customer.

During the Pilot tier, we do not yet have a full IAM/RBAC system. API key access is all-or-nothing. Tenant isolation and role-based access are on the engineering roadmap (see Module 3 of the commercialization plan).

---

## 3. Are camera frames stored after localization?

Yes, by default incoming localization query frames (`/vps/localize` POST) are saved to `storage/queries/{scene_id}/` for debugging and accuracy auditing. This is temporary storage intended to help diagnose localization failures during the pilot.

On request, we can:
- Disable query frame persistence.
- Set an automatic deletion policy (e.g., frames older than 24 hours are purged).
- Log only metadata (frame hash, timestamp, localization result) without retaining the image.

Let us know your retention requirements before the pilot starts.

---

## 4. Does the system use any cloud AI or third-party inference services?

No. All feature extraction, matching, and localization inference runs entirely on the server we provision for your pilot. There is no call to OpenAI, Google Cloud AI, AWS Rekognition, or any other external AI API.

The only external dependency is the Google Maps Photorealistic 3D Tiles API, and only when we run the synthetic data pipeline for benchmarking (not during production localization). If you are running an indoor-only pilot with real-device scans, Google 3D data is not used in your deployment.

---

## 5. How long is data retained?

There is no automatic data deletion in the current MVP. Data persists until:
- You request deletion via the API (`DELETE /scene/{scene_id}/cleanup`) or by contacting us.
- We decommission the pilot environment at the agreed end date.

We recommend agreeing on a data retention window in the pilot contract. A typical setting is:

- Scene maps: retained for the duration of the pilot plus 30 days.
- Query frames: deleted after 7 days or immediately after debugging is complete.
- Evaluation reports: retained for the duration of the pilot.

---

## 6. GDPR and data residency

If your deployment is in the EU or handles EU personal data:

- We can deploy to an EU-resident AWS region (e.g., `eu-west-1`) or Azure region (e.g., `West Europe`).
- Scan video and spatial maps do not inherently contain personal data (they are scene reconstructions, not identity data).
- If camera frames capture individuals (e.g., visitors walking through a scanned area), those frames are query-only localization inputs and are not associated with any user identity by default.
- We do not operate a data processor agreement by default at pilot stage. If your DPA requires one, contact us to arrange it before the pilot begins.

---

## 7. API key access control

API keys are:
- Generated as high-entropy random strings (minimum 32 characters).
- Stored in the backend environment as a hashed value (`API_KEY` env variable).
- Not logged in plaintext in application logs.
- Rotatable: a new key can be issued by restarting the backend with a new environment variable.

There is currently no key expiry or automatic rotation. This is on the roadmap for the Venue and Network tiers.

---

## 8. How do I request data deletion?

During the pilot, contact your designated technical point of contact. We will:
1. Run `DELETE /scene/{scene_id}/cleanup` for each scene to purge raw video, reconstruction, and feature artifacts.
2. Delete the database records for those scenes.
3. Provide written confirmation that deletion is complete.

A self-serve deletion API (with API key auth and audit log) is planned for the Venue tier.

---

## 9. Has the platform been pen tested or security audited?

**Not yet.** The platform is at MVP/pilot stage. We have implemented:
- API key gating on all write and destructive endpoints.
- Input validation (file type and size) on uploads.
- Environment-configurable flags to disable debug and destructive endpoints in production.

We have not yet performed a formal third-party penetration test or SOC 2 audit. If your procurement process requires a security assessment, please discuss with us before the pilot. We can arrange a scoped assessment for enterprise-tier engagements.

---

## 10. Is data encrypted in transit and at rest?

- **In transit:** All HTTP traffic should be served over TLS (HTTPS). For LOCAL deployments, TLS termination is your infrastructure's responsibility (e.g., NGINX reverse proxy with your certificate). We can assist with configuration.
- **At rest:** When using S3 or Azure Blob Storage, server-side encryption is enabled by default (AES-256). For LOCAL deployments, filesystem encryption is your server's responsibility.
